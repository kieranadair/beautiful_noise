# Schema

> **Mid-migration.** Two schemas live here and only one of them is real at any moment.
> `postgres/` is the destination and is **applied** — it built the live Neon database.
> `tables/`, `views/`, `tasks/` are a **record** of the Snowflake schema the app still runs on.
> See `MIGRATION.md` (gitignored, repo root) for which phase is live. The Snowflake half is
> deleted in Phase 6.

```
postgres/   Neon Postgres — hand-maintained, applied, source of truth for the new database
tables/     Snowflake record — one file per table, generated by dump_ddl.py
views/      Snowflake record — POSTER_GALLERY_V
tasks/      Snowflake record — CLEANUP_ORPHANED_STAGE_FILES (suspended; retires unreplaced)
stages.md   descriptive — GET_DDL doesn't support stages
```

## `postgres/` — the new schema

```
schema.sql            tables, constraints, indexes
poster_gallery_v.sql  the gallery's only read surface
roles.sql             the bn_app application role and its grants
apply.py              applies all three, then proves the privilege boundary
```

Build a database from scratch:

```
.venv/bin/python sql/postgres/apply.py
```

Re-check an existing one (after any grant change, or a view rebuild):

```
.venv/bin/python sql/postgres/apply.py --verify-only
```

**These files are applied, not dumped.** The database is built *from* them, so they cannot drift
the way a `GET_DDL` snapshot can. Edit them, don't regenerate them.

**`apply.py` is deliberately not idempotent.** It fails on the first `CREATE` against a database
that already has these objects, rather than silently reconciling. It runs everything in one
transaction, so a failure part-way leaves nothing behind.

### Rebuilding from scratch

`apply.py` refuses to run against a database that already has these objects. To start clean you
must also remove `bn_app`, and that takes three statements in this order — the obvious two fail:

```sql
DROP SCHEMA IF EXISTS public CASCADE; CREATE SCHEMA public;
REVOKE ALL ON DATABASE neondb FROM bn_app;   -- a database-level grant blocks DROP ROLE
DROP ROLE bn_app;
```

`DROP ROLE` on its own reports *"role cannot be dropped because some objects depend on it"* with
`DETAIL: privileges for database neondb`, and the usual remedy — `DROP OWNED BY bn_app` — is itself
refused, because `neondb_owner` is not a member of `bn_app`. Revoking the database grant directly
is the way through.

### The extraction log

`extractions` records one row per AI scan, written before anything is stored and before the user
reviews. Its purpose is a long-term baseline of where the model goes wrong — something you query
occasionally, not machinery the upload path carries.

**The outcome of a scan is derived, never stored.** It isn't known at insert time, and `bn_app` has
no `UPDATE` to set it later. That constraint produced a better design: a derived value cannot drift
from reality.

```sql
select case when not e.is_valid          then 'rejected'
            when p.poster_id is not null then 'saved'
            else 'abandoned' end as outcome,
       e.model, count(*)
from extractions e left join posters p using (scan_id)
group by 1, 2;
```

Accuracy is a join from `e.raw` to the human-confirmed values in `poster_gallery_v` — the review
step produces a labelled dataset for free. `model` is per-row so a model change doesn't blend two
generations into one meaningless average.

Three things worth knowing before you touch this folder:

- **The order in `apply.py` is load-bearing.** `roles.sql` grants `SELECT` on `poster_gallery_v`,
  so the view has to exist first. Getting this wrong is how the first run failed.
- **`events` uses `UNIQUE NULLS NOT DISTINCT`.** Most gigs have no event name, and Postgres treats
  `NULL != NULL`, so a plain `UNIQUE` would let every unnamed gig at the same venue and date insert
  as a separate event — splitting one lineup across duplicates, silently. This constraint is what
  `get_or_insert_event()` used to hand-roll with Snowpark's `equal_null()`.
- **The view's CTE structure is load-bearing.** `credits` and `venues` are pre-aggregated to one
  row per poster before the join, because `bands`/`headliners`/`supports` use non-`DISTINCT`
  aggregates over `band_events`; joining the other two directly fans out and duplicates every band.

`apply.py` verifies the privilege boundary by exercising it — it inserts as `bn_app`, then confirms
`UPDATE`, `DELETE` and `CREATE TABLE` are all refused — rather than trusting the `GRANT` statements
to read the way they behave.

### The future-grants trap

`ALTER DEFAULT PRIVILEGES` is Postgres's equivalent of Snowflake's future grants, and shares its
worst property: it does not show up in a role's grant listing, so an audit that inspects only
current grants can call a role least-privileged while a standing rule quietly hands it every object
created from then on. We set none.

Check with `\ddp` in psql, or `select * from pg_default_acl`. **Note that Neon ships two
platform-level entries of its own** (`cloud_admin` → `neon_superuser`, for tables and sequences) on
every database — so "expect zero rows" is the wrong assertion and will cry wolf forever. Filter for
the role you care about, as `apply.py` does.

## `tables/`, `views/`, `tasks/` — the Snowflake record

Generated by `sql/dump_ddl.py`. These exist so the schema is reviewable alongside the code that
depends on it.

**These files are a record, not a migration.** `GET_DDL` emits `CREATE OR REPLACE`, so running one
against a live schema **drops and recreates the object** — for a table, that means losing every
row. Nothing in this folder should be piped at a live database.

- **`views/poster_gallery_v.sql` replaces the object when applied**, so grants do not carry over on
  their own. (Postgres does not share this problem: `CREATE OR REPLACE VIEW` replaces the
  definition in place and grants survive.)
- **The view's CTE structure is load-bearing**, for the same fan-out reason as the Postgres version.

### Refreshing

```
python sql/dump_ddl.py
```

Reads `.streamlit/secrets.toml` (gitignored) and rewrites the Snowflake folders in place. Unlike
the read-only `SHOW` commands used for auditing, `GET_DDL` runs as a query and briefly resumes the
warehouse.

This script has no future: it is deleted in migration Phase 6 along with the folders it writes.

## What is deliberately not here

- **Credentials, connection strings and account identifiers.** This repository is public. The
  application role's password is generated by `apply.py` and written only to `.env`.
- **Data.** Structure only.

## No orphan cleanup, by design

`CLEANUP_ORPHANED_STAGE_FILES` existed because Snowflake had to stage an image *before*
`AI_COMPLETE` could read it, so rejected, duplicate and abandoned uploads all left files behind.
The Anthropic API takes bytes, so nothing is stored until a human confirms the poster — the R2
write happens one statement before the row that points at it, inside the same `try` that deletes
the object if the save fails. There is no orphan window worth a scheduled job, so that task retires
with Snowflake rather than gaining a Postgres equivalent.

The **grant model** *is* here, in `postgres/roles.sql`. That is a deliberate change from the
Snowflake-era rule, which kept privilege topology off disk entirely — see the note in `CLAUDE.md`
under "Snowflake access for schema/DDL work". Short version: that rule was written while the
topology was a defect worth hiding; a correct least-privilege model is worth publishing, and worth
version-controlling so a rebuild doesn't reconstruct it from memory.

## Known legacy in the Snowflake record

`DESIGNERS` and `POSTERS.DESIGNER_ID` are the frozen single-designer model, superseded by
`CREDITS`/`POSTER_CREDITS`.

Earlier revisions of this file warned that one poster carried a real designer (`designer_id = 401`)
that had to be migrated before `DESIGNERS` could be dropped. **That warning is retired** — those
names were confirmed to be test data, no poster data is being carried into Postgres, and the new
schema has no `designers` table at all.
